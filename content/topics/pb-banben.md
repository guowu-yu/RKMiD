## 一、概念与定位

配置管理（ Configuration Management）是标识、控制、状态记实、审计配置项，确保产品完整性与可追溯性。其中**版本管理**与**配置审计**是其落地的核心手段。在系统集成项目中，软件、文档、硬件配置都可能成为"配置项（CI）"，任一交付物的变更都必须可追、可回、可查。本章是下午案例常见技术背景，也是运维阶段"故障回溯"的基础。

## 二、核心知识

### 1. 版本管理
版本管理是对配置项每次变更进行**标识、存储、比较、合并与回退**的机制。核心是"同一配置项的不同状态用版本号区分，任何版本都可被检索与恢复"。

**版本号规则（主.次.修订）**：
| 位 | 含义 | 递增触发 |
|---|---|---|
| 主版本（X） | 重大架构/不兼容变更 | 重构、对外接口 breaking |
| 次版本（Y） | 较大功能新增（向后兼容） | 新增模块 |
| 修订号（Z） | 小修小补（兼容） | Bug 修复、文档修正 |

例：2.3.1 → 修复后 2.3.2；新增功能 2.4.0；重构 3.0.0。

### 2. 基线（Baseline）
基线是通过**正式评审并纳入配置管理**的配置项集合，是后续开发的"锚点"。常见基线：
- 功能基线（需求规格评审通过）
- 分配基线（概要设计）
- 产品基线（验收版）
基线的变更必须走正式变更流程。

### 3. 配置审计
| 类型 | 审查内容 | 时机 |
|---|---|---|
| 功能配置审计（FCA） | 配置项是否实现规定功能/需求 | 交付前 |
| 物理配置审计（PCA） | 实体与文档/清单是否一致（编号、版本） | 交付/入库时 |

### 4. 发布管理与变更关系
发布管理将"已验证的基线版本"部署到生产/用户环境，含：制定发布计划 → 构建与打包 → 环境准备 → 发布评审 → 部署 → 回退预案。所有发布版本须来源于受控基线，发布即一次变更，须 CCB 批准。

## 三、方法与流程

版本管理典型流程：建立库（开发库/受控库/产品库）→ 检出（Check-out）→ 修改 → 检入（Check-in）→ 打标签/基线 → 评审入库。工具层面常借助 Git/SVN 等实现分支与合并。

配置审计流程：策划审计 → 准备检查单 → 对照 SCM 与实物 → 出具审计 report → 发现不符则开 NCR（不符合项）并跟踪闭环。

## 四、易错点

- **版本 vs 基线**：版本是某配置项的"状态快照"；基线是"被正式认可的配置项集合（版本组合）"。并非每个版本都是基线。
- **受控库 ≠ 产品库**：开发库自由改，受控库变更须审批，产品库仅放发布版。
- **FCA 看功能、PCA 看实体**：考试常把二者混考，记住"功能对需求、物理对清单"。
- 版本号"回退"是恢复到旧版本，不等于"删除变更历史"。
